System architecture

The chatbot is an agentic tool-use loop. The model never sees the raw scorecard — it must call read-only tools to fetch each number, which makes every factual claim traceable to a measurement. It runs two ways from the same coaching_chat.py: locally via serve_demo.py + the Codex CLI (what this page is using), or in the cloud on AWS Lambda + Claude.

Why tool calling

The old Q&A dumped the whole scorecard into one prompt and hoped the model reported the right metric. Here the model can't cite a number it never fetched — grounding is enforced at the data layer, and the tool log is an audit trail (the 🔧 trace under each answer).

Two runtimes, one agent

Local: serve_demo.py + the Codex CLI — no key, runs on your machine. Cloud: AWS Lambda (scale-to-zero, CPU-only) + Claude via the Anthropic API. Same coaching_chat.py loop, tools, and verifier — the backend is a config flip.

The tools

  • list_indicators — what can be answered
  • get_indicator — one metric vs tour range
  • compare_indicator — this swing vs another swing
  • get_flagged_observations / get_swing_summary
  • explain_term — glossary lookup, no inventing

Stateless & bounded

The browser keeps the conversation; each turn posts {clip_id, question, history[]}. The server reloads a pre-computed scorecard (no GPU) and a hard 6-round cap plus history/size limits bound cost. Cloud scales to zero; nothing runs between questions.

How it stays grounded

Three layers keep answers honest — the same discipline that got the explanation layer to a held-out grounding score of 1.000, now applied to a conversation.

1 · Tools are the only source of truth

The scorecard is never pasted into the prompt. To say “your tempo is 3.1”, the model must call get_indicator("tempo_ratio"). No call → no number.

2 · A clear refusal taxonomy

Unmeasured topics (ball flight, grip, club face) → the metric isn’t in list_indicators. Low-confidence metrics (arm bend from one camera) → the tool returns reliable:false. Fix/advice → out of scope. In all three it declines instead of guessing.

3 · Deterministic transcript check

verify_chat_grounding() re-reads the tool log after each answer and flags a low-confidence leak, an in/out-of-range claim with no matching fetch, or prescriptive language — the green/amber badge under every reply.

Tolerant by design

Any model or network failure degrades gracefully to a short apology, never a crash or a made-up answer — matching the shipped CLIs.
